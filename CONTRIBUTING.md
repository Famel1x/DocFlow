## Как сообщить об ошибке (Bug Reports)

Перед тем как создать Issue:
1. Убедитесь, что проблема еще не обсуждалась в разделе [Issues](https://github.com/).
2. Проверьте поведение на последней версии ветки `main`.

Создавая Issue, включите:
* **Четкий заголовок:** кратко формулирующий суть сбоя.
* **Шаги для воспроизведения:** точная последовательность действий, формат загруженного файла (PDF, DOCX, PPTX, XLSX), параметры правил `@mode`.
* **Ожидаемое и фактическое поведение:** что должно было произойти и что произошло в реальности.
* **Логи и снимки экрана:** консольный вывод uvicorn, трассировки ошибок (Traceback), скриншоты интерфейса при необходимости.
* **Окружение:** ОС (Windows / Linux / macOS), версия Python, браузер.

## Предложение новых функций (Feature Requests)

Если у вас есть идея по расширению функционала (например, поддержка новых форматов таблиц, улучшение алгоритмов OCR или новые директивы для движка правил):
1. Откройте Issue с типом **Feature Request**.
2. Опишите сценарий использования и проблему, которую решит предлагаемое нововведение.
3. Предложите возможную архитектуру реализации.

## Процесс разработки и Pull Request

1. **Форкните репозиторий** и клонируйте его локально:
   ```bash
   git clone https://github.com/<ваш-аккаунт>/DocuFlow.git
   cd DocuFlow
   ```
2. **Создайте изолированное окружение:**
   ```powershell
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   pip install --upgrade pip
   pip install -r requirements.txt
   ```
3. **Создайте ветку под вашу задачу:**
   ```bash
   git checkout -b feature/awesome-table-parser
   # или для багфикса:
   git checkout -b fix/vmerge-spanning-bug
   ```
4. **Внесите изменения и протестируйте их** (см. раздел [Тестирование](#тестирование)).
5. **Закоммитьте изменения** в соответствии с [конвенцией коммитов](#формат-коммитов-conventional-commits).
6. **Отправьте ветку в ваш форк:**
   ```bash
   git push origin feature/awesome-table-parser
   ```
7. **Откройте Pull Request** в ветку `main` основного репозитория, заполнив описание изменений.

## Стандарты оформления кода

* **Python:** Придерживайтесь стандартов [PEP 8](https://peps.python.org/pep-0008/).
* **Типизация:** Добавляйте аннотации типов (Type Hints) для параметров функций и возвращаемых значений.
* **Документирование:** Все ключевые классы, методы парсеров и эндпоинты FastAPI должны содержать понятные docstring.
* **Фронтенд:** Чистый, семантичный HTML/CSS/JS без лишних сторонних зависимостей и тяжелых фреймворков.

## Тестирование

Перед созданием Pull Request обязательно запустите комплекс тестов проекта:

```bash
python test_english_suite.py
```

Если вы добавляете новый парсер или меняете поведение движка правил:
* Добавьте соответствующие тесты в тестовый сьют.
* Приложите минимальный пример тестового файла в каталог `test_files/`.

## Формат коммитов (Conventional Commits)

Мы рекомендуем использовать стандарт [Conventional Commits](https://www.conventionalcommits.org/):

* `feat: ...` — добавление нового функционала
* `fix: ...` — исправление ошибки
* `docs: ...` — изменения в документации (README, гайды)
* `style: ...` — форматирование, пробелы, точки с запятой (без изменений логики кода)
* `refactor: ...` — рефакторинг кода без добавления функционала и исправления багов
* `test: ...` — добавление или изменение тестов
* `chore: ...` — обновление зависимостей, служебные скрипты, конфигурации сборки

**Пример:**
```text
feat(parsers): add support for merged cells in multi-page docx
fix(rules): resolve case-insensitive header mapping in mode row
docs: update security policy and community standards
```
